# MC 量体三端交互原型

本仓库包含管理后台、裁缝端和客户端三个独立静态入口。

根目录 `index.html` 提供三端统一预览入口，GitHub Pages 通过 `.github/workflows/deploy-pages.yml` 自动部署静态文件。

## 访问入口

- 管理后台：`/measure_admin/`
- 裁缝端：`/tailor/`
- 客户端：`/client/`

## 本地运行

在仓库根目录执行：

```bash
python3 -m http.server 8767
```

然后访问：

```text
http://localhost:8767/measure_admin/
http://localhost:8767/tailor/
http://localhost:8767/client/
```

各端当前均为静态交互原型，不连接生产数据库。详细交互和数据规则见各目录内的 README。

## 原型维护范围

- 后续需求默认只修改本仓库 `demo_measure_git/` 内的静态交互原型及其 README 文档。
- 不同步修改上级项目中的正式源码、Python 服务端、SQLite 数据库或部署配置。
- 只有在需求中明确写明“修改源码”“接入服务端”“修改数据库”等要求时，才调整 `demo_measure_git/` 以外的正式实现。
- 管理后台原型功能以 `measure_admin/index.html`、`measure_admin/app.js`、`measure_admin/styles.css` 和 `measure_admin/README.md` 为准。

## 订单执行与售后（2026-09-15）

正向流程：服装确认 → 预约量身 → 完成量身 → 已下单到工厂 → 工厂交付，待派送 → 已交付。

- 按员工与订单匹配进度；员工签字确认、有效预约、裁缝提交量体记录驱动前段进度。
- 管理后台“订单管理 → 执行进度”按员工顺序确认工厂下单、工厂交付与最终交付。
- 客户端订单卡展示全部节点、已完成状态与下一步。

售后流程：提交售后 → 门市收货 → 已下单到工厂 → 工厂交付，待派送 → 完成派送。

- 员工在订单卡“提交售后”选择退换服装、数量，填写逐项修改要求及补充说明。
- 服装优先使用员工已确认明细；未确认时使用所属订单按性别配置的服装及默认数量。数量必须为正整数且不超过对应数量，每项修改要求必填。
- 员工到门市退还后，后台“售后管理 → 查看详情 / 处理”逐项录入实际签收数量（允许少于申请数量，未带来的填 0，合计至少 1 件），填写签收人后确认收货；保留签收时间、备注和实收明细。
- 门市可分次签收，也可填写原因关闭单项服装；仍需处理的服装收齐后才能送厂。门市收货后的工厂和派送节点只能顺序推进；批量操作要求全部所选记录可进入相同的下一阶段，完成派送后不再修改。
- 后台可按员工 / 申请编号、单位、提交日期、状态筛选，导出全部筛选结果（不限当前页）。CSV 按服装逐行输出，含申请数量、实际签收数量、修改要求、状态及签收信息。
- 再次售后创建独立申请，保留上次记录。

## 预约管理

时段绑定订单，包含地址、日期、起止时间、容量、是否支持超额及开放状态。员工仅查看当前订单的可预约时段；已有预约时先提示地址与时间，可查看并取消。后台支持批量导出预约明细。

## 数据与兼容

- `shared/workflow.js` 统一初始化三端演示数据、迁移旧售后状态并计算进度；直接首次打开任一端即可初始化数据。
- 三端共享同源 `localStorage`，客户端和后台监听其他标签页的数据变动。仅为当前浏览器的原型联动。
- 旧版“已登记 / 已处理 / 已完成”映射为“提交售后 / 门市收货 / 完成派送”；更早版本按其旧语义迁移。旧记录的内容和状态历史保留，不伪造签收人或签收时间。
- 发布工作流包含共享脚本，仅发布静态运行文件。
